Binary Chunk Organizer Format By UnnamedBruh Version 1 This document is an independent exercise in writing specifications. It defines the Binary Chunk Organizer Format (BCOF), which is heavily inspired by the Resource Interchange File Format (RIFF).

  1. Phrases
    The following vocabulary applies in this document.
    1. "Thing" refers to a rule, definition or specification.
    2. "Must" is an absolute requirement of a thing.
    3. "Must not" is an absolute prohibition of a thing.
    4. "Should" is a recommendation to implement a thing.
    5. "Endian-neutral" means a value's binary structure is unaffected regardless of the preferred byte order of an architecture. This applies to writing or reading binary data into/from a file.
    6. "Integer" means a block of memory that must be interpreted as a little-endian unsigned integer.
    7. "Fail gracefully" means to stop parsing the BCOF format, or throw an error. The exact behavior is up to the implementation.
    8. A backslash followed by a three-digit number is an octal escape. \0 is an octal escape representing 0. \1 is an octal escape representing 1. etc.
    9. A "byte-level string" is encoded strictly in extended ASCII (ISO-8859-1), where each character is a fixed 8 bits. Strings that were originally in another encoding must be re-encoded into extended ASCII (ISO-8859-1); this rule applies when overwriting a field. If characters cannot be represented in ISO-8859-1, they should be replaced with question marks (?). Its final length is calculated by finding the last null byte.
  2. Core Structure
    The Binary Chunk Organizer Format is a file format that intends to organize binary data into machine-readable chunks. This can be useful for situations where unorganized information can be undesirable. It is organized into a header, and a list of chunks.
    Below is its structure.
    • All Binary Chunk Organizer Format (BCOF) files must begin with a header. Its structure is:
      1. hdr: An 8-byte, endian-neutral string whose value is "BCOF\0\0\0\0" (without quotes), where each \0 is a null byte.
      2. filesize: An 8-byte integer that specifies the file size (in bytes). The file size includes this header, the chunk sizes, and all the padding.
      3. version: A 2-byte integer that specifies the version of the BCOF format. This must be 1 for the version of this document.
      4. reserved: A reserved block of data that is 6 null bytes.
      5. reserved2: A reserved block of data that is 8 null bytes.

      Each field is not padded to a number of bytes, unless specified otherwise.
      In this example, a block of data is represented using hexadecimal bytes. 
      42 43 4F 46 00 00 00 00 <- Header
48 00 00 00 00 00 00 00 <- Filesize (value is 72)
01 00 <- Version (value is 1)
00 00 00 00 00 00 <- Reserved (initialized to 0)
00 00 00 00 00 00 00 00 <- Reserved2 (initialized to 0)

Total Size: 32 bytes (multiple of 8)

      Notes:
      • If the implementation does not recognize the version of the BCOF format, it should fail gracefully.
      • If any byte in the reserved and reserved2 fields are not null, and the version is 1, the implementation must fail gracefully.
    • What follows after the header is:
      1. chunkList: A variable-size array of chunks whose structure is the chunks themselves, or nothing if there are no chunks.

      A chunk is structured as:
      1. chunkHdr: An 8-byte, endian-neutral byte-level string whose value is arbitrary. If its size is below 8 bytes, it must be padded with null bytes. If it exceeds 8 bytes, it must be truncated to the first 8 bytes. Examples include: "example\0". "name\0\0\0\0". "settings". "erroneou" (originally "erroneously"). Each \0 indicates a null byte.

        Edge case examples include:
        • "one\0two\0": The first null byte must be treated as part of the string. The second must be treated as padding.
        • "\0\0\0\0\0\0\0\0": The field is an empty string value. Each null byte is padding.
        • "pear\1\1\1\1": A \1 indicates a byte with the value of 1. Each 1-value byte must be treated as part of the string.
        • "ü5·¼ÆM4Â": The field is 8 bytes.
      2. chunkSize: An 8-byte integer that specifies the size of the binary data (in bytes). The size does not include the chunkHdr, chunkSize, flags nor its padding.
      3. flags: An 8-byte integer that must be 0 for the version of this document.
      4. binaryData: A variable-size block of data whose structure is arbitrary.

      The binaryData is padded to an 8-byte block. The padding bytes are located at the end of the binaryData, and must be null.
      This is an example of a chunk. The formatting is the same as the previous example. 
      65 78 61 6D 70 6C 65 00 <- ChunkHdr (value is "example\0")
0C 00 00 00 00 00 00 00 <- ChunkSize (value is 12)
00 00 00 00 00 00 00 00 <- Flags (value is 0)
48 65 6C 6C 6F 2C 20 42 43 4F 46 21 <- BinaryData (value is "Hello, BCOF!")
00 00 00 00 <- Padding (so that the binaryData is padded to an 8-byte block)

Total Size: 40 bytes (multiple of 8)

      Notes:
      • If the implementation does not recognize a chunk or its binary data, it must not throw an error. Instead, it must either ignore that chunk, or stop parsing the format. The exact behavior is implementation-defined.
    • Below is a list of chunks that are reserved by this specification, where a string literal represents its chunkHdr:
      1. "metadata"

        This chunk represents the metadata for the Binary Chunk Organizer Format file. Its binaryData is a list of metadata chunk fields, which is structured as those metadata chunks. This chunk cannot appear more than once.
    • Each metadata chunk field is structured as:

      • name: A 12-byte, endian-neutral byte-level string.
      • size: An 8-byte integer representing the number of bytes of value. It does not include the padding.
      • id: An 8-byte integer whose value represents an identifier for this metadata chunk. If a metadata chunk field has the same name as another, its id must be unique. Otherwise, the id can be the same as the id of another field. For an example:
        • In a metadata chunk that has:
          • "name" as one field, and
          • "name" as another

          Those fields' ids must be unique, because they describe fields that have the same name.
        • And in a metadata chunk that has:
          • "name" as one field, and
          • "description" as another

          Those fields' ids don't have to be unique, because they describe two different fields.
      • value: An arbitrary-length, endian-neutral string that is encoded in extended ASCII (ISO-8859-1). This field is padded to an 8-byte block using null bytes. The padding is at the end of the string. It must not be empty.


      This is the list of allowed metadata chunks, where a string literal represents its name, and "document" refers to a BCOF file:

      Humorous/Joke Fields

      1. "humoroustext": Any text that does not serve a particular purpose. It can be used to include text that is not serious. Examples include: "Your mom.", "I broke my back when I turned off the TV yesterday.", "Your table is secretly plotting a crime.", "im crine, lol...", "I tore out my hair while making this. I seriously hope it does something good." UnnamedBruh, the creator of the BCOF format, agrees with the latter statement.

      Descriptions/Legal

      1. "consequences": A description or summary of potential legal actions that will be taken upon violating the rights of the legal entities. This does not include threats, in spite of the generic "consequences" naming. This can be desirable when the "license" field does not explicitly name them. If exact legal actions are unknown, or must not be included for any reason, a generic "Rights to this document terminate upon violating the license.", or "Do not use this document if you do not agree to the license." will do. Threats like "You will become a ghost someday." do not belong in this field.
      2. "description\0": A description or summary of the document that has an arbitrary word count. It must be relevant to the "title", "name" or "copyright" fields, or the contents of the document. Examples include: "A grayscale image of the Moon in a portrait orientation.", "JavaLava2345 is a programmer that's famous for reciting the longest Spanish word."
      3. "disclaimer\0\0": A cautionary warning, or description. It specifies mandatory information, or information that must be known before the document can be used. Note that "warnings" like "Contains sensitive information. Access only if you are 18+." are insufficient, or do not specify reasons to take cautionary action. Age limits like 18+ are ambiguous for that exact reason. Examples include: "That information can be misused by a bad actor. Do not disclose publicly.", "The information includes names and ages that are tied to real people.", "This document contains legally protected information. It must not be disclosed.". Bad examples include: "Viewer discretion advised.", "Caution is necessary to handle this file.", "Access if you are 18+.", "Contains sensitive information." Age gates only limit content to an audience older than that age. They do not make content "safer" or "mature," nor do they guarantee that the user is above that age. Age gates also contradict one of the philosophies of the BCOF format. It is not limited to any particular age.
      4. "license\0\0\0\0\0": A brief description of the license's terms, and/or steps to view the full license text. A brief, casual note of what the user can do with the document (like Don't use it in commercial games.) is allowed, but heavily discouraged, because it can be difficult to lawfully enforce. Examples include: "Commercial, academic, educational and entertainment uses permitted.", "Released into the public domain. See the Unlicense for more details.". Descriptions such as "All rights reserved." may be vague, given the purpose of this field. It is generally more practical to write "[company] reserves the rights to this material," where [company] is the legal entity (or legal entities) that reserved the rights to the document.
      5. "purpose\0\0\0\0\0": Reasons for the existence, production or synthesization of the document. It can also include the artists' desires or needs leading to its creation. Examples include: "To provide multiple calculations of the same data plot.", "I thought that 32-bit sizes were too limited to store the binary data.", "Compiled HTML files, or generic HELP files are obscure enough to be meaningless today.", "This exists to safely contain a large list of programs that use many escaped characters." Bad examples include: "RIFF documents aren't good.", "My boss yelled at me for trying to store it in text.", "Because why not?", "To prove conspiracy theories that they're true." The latter is ambiguous, because "conspiracy theories" can refer to any claim, in spite of its association with obvious fallacies.

      Titles/Names

      1. "contexttitle": Additional context that cannot be obtained from the title, or the brief description alone. Examples include: "Painted during 1503-1519", "A calming song", "Contains names and ages".
      2. "copyright\0\0\0": The official title(s) of a legal entity (or legal entities), and/or the full names of users that obtained or exercised the rights to the original material. It should be accompanied by a copyright date. This does NOT cover nicknames, or alternative names to legal entities. This can cover legal entities that hold the rights to other businesses or organizations, if naming all of them is undesirable. Examples include: "GreenGrass Studios, 2000-2008", "John Doe, 2026", "1989 Formal Action Corp.".
      3. "name\0\0\0\0\0\0\0\0": Names, or nicknames of the original artists or creators of the material. This also includes the usernames of artists, and optionally an online platform associated with those usernames. Examples include "Jane Doe", "Garbleson Guiro", "JavaLava2345", "@UnnamedBruhGD (YouTube)".
      4. "title\0\0\0\0\0\0\0": The title, or a brief description of the document. This is not the name of the original artists or creators. Examples include: "Mona Lisa", "A Lulling Tune", "Binary Document".
